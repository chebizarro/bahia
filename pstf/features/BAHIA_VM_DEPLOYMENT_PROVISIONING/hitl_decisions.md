# Governed decisions and contract handoff

Authority: the supplied canonical plan's **Lifecycle classes** and **Bahia feature design**, plus the implementation plan's **A. Phase 0**. Both source plans already exist and were left unchanged. This artifact records the supplied decisions and Item A implementation semantics; it does not claim a new live-host or security approval.

## Supplied policy decisions

- `persistent_vm` belongs to Bahia. `loom_firecracker_job_microvm` and `loom_qemu_job_domain` belong to Loom. Classes are required, never inferred from runtime names, images, OS, prefixes or worker advertisements.
- Pilot policy revision 1 is opt-in `VirtualizationHost.PilotPolicy`, not a host default. GNOME: 8 vCPU / 24 GiB / 100 GiB. Windows: caller-selected 6–8 vCPU / 16–24 GiB / 100–120 GiB. The source wording “approximately 220 GiB” is enforced as exactly 236223201280 bytes; aggregate CPU/RAM ceilings are 16 / 68719476736 bytes.
- Tier 2 uses a distinct operator, exact request hash/generation/provider fingerprint, at most 30-minute expiry and single-use consumption. Authentication and approver authorization belong to C; a database approval record alone is not authorization.
- Checkpoints are cold coordinated manifests. UEFI requires NVRAM, TPM requires swtpm state, Firecracker requires kernel/rootfs and forbids NVRAM/TPM. B must reject TPM clones unless it verifies identity reset/rekey support; no silent TPM removal.
- Public connections are SSH/RDP/HTTPS or an authorized console resource reference. No URL userinfo, tokens, passwords, provider sockets, management URIs or automatic public exposure. Endpoint/storage/trust policy identifiers are opaque UUID references, not paths or credentials.
- Bootstrap input is `VMBootstrapBinding` with only `SecretRef.ID` populated. C resolves authoritative metadata and authorizes references. Plaintext delivery is operation-scoped through `VMBootstrapDelivery` / `VMBootstrapGuest`; `VMProviderOperation` cannot be JSON-marshaled.
- Administrative Loom tools are proposed required endpoint contracts, not evidence that any deployed endpoint implements them. D must discover protocol support and fail unavailable without calling SubmitJob, a shell, another host or a local runtime. Worker identity is the existing `Worker.PubKey` contract (`WorkerPubKey` here), not a fabricated worker UUID.

## Persistence contract for C, D and E

- Use `NewPgVirtualizationRepository(pool)` and its typed resource accessors. Every call is organization-scoped. `Get` returns `ErrNotFound`. `Create` requires schema 1 / generation 1 and assigns timestamps. `Update` requires generation `expected+1`; immutable creation fields must match. Images are insert-only.
- Desired writes must not contain observations. A fetched observation may belong to an older desired generation and retains its own timestamp. Clear `Observation` before submitting desired updates. Install sessions separately with generation/session CAS; an incoming observation cannot install a session. Sequence numbers are strictly increasing within a session.
- Plain updates cannot change provider ownership identity. An approved tier-2 `define` with a recreate plan may rebind the provider identity while retaining the stable deployment UUID only after the old provider resource is confirmed absent in the current session and its persistent capacity reservation is released. Admission consumes approval, writes the new generation and reserves the new target atomically; old observations/session are cleared on rebind. Retained historical checkpoint identities do not migrate.
- `VMOperationAdmission.ExpectedGeneration` is the prior resource generation (0 for initial define). `VMOperation.ExpectedGeneration` matches it. `ResourceGeneration` is the resulting desired generation. Approval binds the prior generation plus exact request hash/fingerprint. Caller cancellation cannot undo committed admission.
- `AdmitOperation` atomically applies an optional desired revision, reservations, approval consumption, operation and snapshot journal. Same tenant/idempotency key and request content returns the original operation. C computes the canonical request hash and validates the complete change plan; B revalidates provider identity/fingerprint and image trust immediately before effects.
- There is one nonterminal operation per deployment. `unconfirmed` is nonterminal. `WithOperationLock` holds a dedicated PostgreSQL session lock across provider work; admission checks the same lock. It is not an external fencing token. Lock-loss/unlock failure is reported unconfirmed, and C must inspect before recovery rather than blindly replay effects.
- `delete` requires explicit `DeleteTarget` (`deployment`, `checkpoint`, `export`). Forced stop is only an explicit tier-2 deployment-delete option. Artifact deletion does not mean parent VM deletion. Artifact source/target IDs remain on the durable operation for recovery.
- Reservations cover persistent allocations even while stopped, plane capacity once (never per-job again), and checkpoint/export bytes. Host writes/admission are serialized per organization. Growth must fit governed quota and a fresh current-session provider capacity observation. The current free-capacity gate is deliberately conservative: all reservations must fit reported free capacity, rather than assuming that a provider has already materialized earlier reservations. B/C must not bypass this gate through thin provisioning. Release requires verified absence/drain/deletion and terminal operations.
- Checkpoint/export manifests freeze after leaving `creating`. Export copies may use different private storage object IDs, but component kinds/hashes/sizes must match the source checkpoint. Parent records are retained for audit.
- `VirtualizationResourceChange` contains immutable resource/observation snapshots and approval correlation. Per-organization journal allocation is serialized with commit order, avoiding late-committing lower-cursor loss. E must build public DTOs from these snapshots; do not treat private endpoint/storage/trust references as public provider locations.
- Capability contribution is separate from generic worker advertisements. `EffectiveExecutionPlaneCapabilities` requires exact current generation/session, fresh authenticated successful probe, matching package/config/image/capacity/concurrency and enabled state. Failure, expiry, disabled/draining/unavailable state, pin mismatch or Windows claims yields no contribution. D additionally checks scheduling and available capacity.

## Integration ownership

- B (`bahia-xv6vl`): implement `PersistentVMProvider`, actual trusted artifact/provenance verification, bounded allowlisted driver effects, identity checks, coordinated checkpoint mechanics and guest bootstrap protocol support. No changes to the existing `Hypervisor` were made by A.
- C (`bahia-kw93u`): implement auth/RBAC, request hashing, mutability classification policy, approval authorization, audited secret resolution, operator lifecycle and inspect-before-replay recovery. Provider results, not transport acknowledgments, determine completion.
- D (`bahia-1wh79`): implement `ExecutionPlaneClient`, authenticated canonical observations, endpoint support, probe/session ordering, plane admission and worker capability contribution. `Apply` acknowledges only; `Probe` must return actual authenticated live evidence, not infer success from its acknowledgment or EOSE.
- E (`bahia-8f30n`): wire the repository constructor/services, DTOs, canonical projections and metrics. No registration, existing provider, API, telemetry or unrelated validator files were changed by A.

No production host, endpoint implementation, image build, pilot, restore drill or soak is accepted by these domain/database tests. Those remain under the parent epic and downstream work items.
