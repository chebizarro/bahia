# Soul Factory sidecar deploy and first-provision runbook

This runbook is for a human operator deploying the OpenClaw SoulFactory runtime sidecar. The example host name `max` and paths are illustrative; use the fleet's supervised-service and secret-management conventions.

## 1. Build and install

On a trusted Bahia build host:

```bash
go build -o ./bin/openclaw-soulfactory-control ./cmd/openclaw-soulfactory-control
go build -o ./bin/openclaw-soulfactory-sidecar ./cmd/openclaw-soulfactory-sidecar
```

Install both binaries on the runtime host, for example under `/opt/bahia/soulfactory/`.

## 2. Persist the sidecar runtime key

Create a dedicated Nostr key for the sidecar. This key signs public `30317` capabilities and `38386` results; it is not an agent key and is not the Signet controller identity.

```bash
install -d -m 0700 /etc/bahia/soulfactory
install -m 0600 /dev/null /etc/bahia/soulfactory/sidecar.key
# Write one nsec or hex secret generated by the fleet-approved key tool.
```

Pass this file through:

```text
-private-key-file /etc/bahia/soulfactory/sidecar.key
```

Alternatively, `OPENCLAW_SOULFACTORY_PRIVATE_KEY` remains supported. Do not configure both the file and environment source. `SOULFACTORY_SIDECAR_NSEC` is not a recognized variable.

## 3. Configure the control wrapper

The packaged wrapper supports:

```text
soulfactory.provision,soulfactory.update,soulfactory.persona.update,soulfactory.revoke
```

For real execution use `OPENCLAW_SOULFACTORY_RUNTIME_MODE=existing-container` and set `OPENCLAW_SOULFACTORY_CONTAINER`. Dry-run mode renders deterministic state/workspace files without calling the OpenClaw CLI.

If `openclaw` is not on PATH, set `OPENCLAW_SOULFACTORY_OPENCLAW_BIN`. The older `OPENCLAW_SOULFACTORY_BIN` name is not read by the wrapper.

## 4. Start the sidecar

Use the Bahia SoulFactory controller pubkey (resolved from the controller's Signet identity) as the trusted controller. Configure runtime/control relays, not ngit repository relays.

```bash
/opt/bahia/soulfactory/openclaw-soulfactory-sidecar \
  -private-key-file /etc/bahia/soulfactory/sidecar.key \
  -command /opt/bahia/soulfactory/openclaw-soulfactory-control \
  -methods soulfactory.provision,soulfactory.update,soulfactory.persona.update,soulfactory.revoke \
  -trusted-controller-pubkeys '<soulfactory-controller-pubkey>' \
  -relays wss://relay.example.com \
  -control-relays wss://relay.example.com \
  -health-addr 127.0.0.1:8081 \
  -idempotency-store /var/lib/bahia/openclaw-soulfactory-sidecar-idempotency.json
```

Deploy it as a supervised service. Persist both the key file and idempotency store with restrictive permissions. The JSON store lets exact `38384` replay after restart republish the cached `38386` without repeating local side effects.

The relay bus handles stored-event backfill then remains live, reconnects with backoff, and retries a subscription after NIP-42 auth when a relay sends `auth-required:`.

The sidecar exposes `GET /health` for process liveness and `GET /ready` for functional readiness on `-health-addr` (default `127.0.0.1:8081`). Readiness returns HTTP 200 only after the kind-`30317` capability was accepted by a relay and the control subscription reached EOSE. Before both conditions it returns HTTP 503 with `capability_published`, `subscription_eose`, and `last_error` fields. Supervised-service healthchecks must use `/ready`, not a PID-only check; use `/health` only as a separate liveness probe.

## 5. Verify capability publication

Subscribe for factory-authored runtime capability kind `30317` from the sidecar runtime pubkey. The latest event must include:

- `schema=soulfactory-runtime-capability/v1`;
- `control_schema=soulfactory-runtime-control/v1`;
- `runtime=openclaw`;
- the four configured methods;
- `controller_pubkeys` containing the SoulFactory controller;
- accurate relay hints.

If `/souls/new` cannot select it, verify event signature, relay visibility, runtime key, controller key, schema, and method list.

## 6. Provision end to end

1. Open `/souls/new`.
2. Select the compatible OpenClaw `30317`.
3. Save the signed `31952` draft.
4. Publish the correlated `5950`.
5. Observe:
   - `6950` step 1: draft/LLM generation;
   - step 2: Signet `agent/provision`, then configured NIP-29 assignments;
   - step 4: kind-`0` profile signed by the Signet-held agent identity;
   - step 8: `38384` → sidecar/wrapper → correlated `38386`, then Bahia service/deployment registration.
6. Confirm final active `31951` and terminal success `7950`.

The public `31951`, `7950`, and relay-visible `38384` checkpoint must not contain an agent private key or Signet bunker URI/secret. The bunker URI is private runtime handoff only.

If configured `soul_factory.nip29_groups` fail AUTH or relay `OK`, provisioning fails closed during step 2. Resolve controller authorization/NIP-42 before retrying.

## 7. Restart and late-result verification

After a controlled sidecar restart, replay the exact `38384` and confirm it republishes the cached result without rerunning OpenClaw commands.

The Bahia reactor separately backfills queued `5950` and `1950` events (up to 1000 of each per relay subscription) and stored `38386` results. A late valid success `38386` can reconcile an earlier deploy-stage timeout without repeating earlier provisioning stages.

## 8. Rollback

To stop new OpenClaw runtime bindings, stop the sidecar. Existing Signet-held identities remain under Signet custody. Use a signed SoulFactory revoke action for agent-specific teardown.

Do not delete the idempotency store during a routine rollback; doing so removes restart replay protection.
