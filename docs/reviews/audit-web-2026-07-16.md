# Production-Readiness Audit — Bahia Web + pkg/client + pkg/discovery

- **Date:** 2026-07-16
- **Scope:** `web/**` (SvelteKit app: `src/lib`, `src/routes`, `static`, `docker-entrypoint.d`) **excluding** `web/tests`; plus Go `pkg/client` and `pkg/discovery`.
- **Out of scope (other agents):** `internal/`, `cmd/`, `web/tests`.
- **Method:** Read the core transport/auth layers directly; dispatched three read-only probes (auth, stores, routes); traced the repository-list and auth flows end-to-end; verified every load-bearing claim against the source before reporting. Read-only — no code was modified.

## Context

This is a **signer-first, Nostr-native** dashboard. The documented architecture (see `web/README.md`) is:
- capability + relay bootstrap from Nostr discovery events;
- shared state hydrated from relay-backed read models;
- writes published as **signed Nostr events**, resolved by correlated result events;
- sensitive flows over **encrypted** Nostr request/result relays;
- a narrow REST surface (`src/lib/api/client.js`) retained only for SBOM/Blossom and a few compatibility CRUD paths (orgs, secrets).

**The real authorization boundary is server-side signed-event contract validation, not the browser.** Client-side auth state and route guards are UX/defense-in-depth, so the auth findings below are scored as correctness/reliability/defense-in-depth issues, *not* remote privilege escalation. They are still production defects: they make the UI assert identity, authentication, and access that were never actually established.

### Positives worth recording
- **No hardcoded relay URLs, pubkeys, or endpoints** in production code. Relay topology is discovery-driven; the only literal `wss://` strings are input placeholders and test fixtures.
- **`pkg/discovery/resolver.go`** and **`pkg/client/operator_discovery.go`** are genuinely production-grade: real inbound-event + signature validation, trusted-author allowlists, EOSE-gated selection, reconnect backoff, and NIP-42 AUTH handling. No fake completion found.
- **`pkg/client` REST write methods** (`CreateService`, `DeployServiceRuntime`, `CreateDeploymentIntent`, `Rollback`, `CreatePolicy`, `ScanAdoption`, etc.) are *intentional* deprecation stubs that return an explicit "publish a signed Nostr event instead" error — correct migration behavior, not fake completion.

## Findings

### P1-1 — Fake CI enrichment reports canned data as a successful load
- **Severity:** P1
- **Category:** fake-completion
- **File:** `web/src/lib/stores/repositories.svelte.js:139-158`

```js
export async function enrichRepositoriesWithCI(repoList) {
  const currentSeq = ciMeta.requestSeq + 1;
  ciMeta.requestSeq = currentSeq;
  ciLoading.value = false;
  ciError.value = null;

  repoList.forEach(r => {
    r.ci = r.repoCoordinate
      ? { state: 'empty', lookup: null, error: null }
      : { state: 'unsupported', lookup: null, error: null };
  });

  if (ciMeta.requestSeq === currentSeq) {
    ciMeta.lastLoadedAt = Date.now();
  }
}
```

**Evidence / why not production-ready:** The function name and call site (`loadRepositories()` invokes it "non-blocking" after fetching repos) imply a real CI status lookup over Nostr/API. It performs no I/O: it never sets a loading state, assigns a hardcoded `state: 'empty'` / `'unsupported'` object to every repo, and stamps `ciMeta.lastLoadedAt = Date.now()` to signal a completed load. Every repository will forever show "empty/unsupported" CI regardless of actual CI state. This is a placeholder masquerading as a completed feature.

**Recommended fix:** Either implement the real CI lookup (query the CI read model / relay by `repoCoordinate`) with genuine loading/error states, or delete the enrichment call and the `ci*` store state and render "CI status unavailable" explicitly so the UI does not imply data it does not have.

### P1-2 — Failed login silently restores a stale persisted session as "authenticated"
- **Severity:** P1
- **Category:** reliability
- **File:** `web/src/lib/stores/auth.svelte.js:648-673` (`login()` catch block)

```js
} catch (error) {
  console.error('Login failed:', error);
  const persisted = loadPersistedSession();
  if (persisted) {
    updateAuthState({
      status: 'authenticated',
      pubkey: persisted.pubkey,
      relays: persisted.relays,
      authMethod: persisted.authMethod || 'nip07',
      capabilities: persisted.authMethod === 'nip46' ? getNip46Capabilities() : getNip07Capabilities(),
      nip46: persisted.nip46 || null,
      lastAuthenticatedAt: persisted.lastAuthenticatedAt,
      profile: persisted.profile || null,
      error: null
    });
  } else {
    updateAuthState({ status: 'error', error: error.message });
  }
  throw error;
}
```

**Evidence / why not production-ready:** When the user explicitly clicks "sign in" and the signer flow **fails or is rejected** (`getNip07PublicKey()` throws), the catch block swallows the failure into an `authenticated` state pulled from `localStorage`, with `error: null`. The user is shown as logged in as `persisted.pubkey` even though no signer just proved control of that key. The same pattern exists in the NIP-46 connect path (`loginWithNostrConnect`, catch at `auth.svelte.js:716`). Result: a rejected/broken signer produces a UI that claims a working authenticated session; the first action that actually needs a signature will then fail confusingly. (`throw error` still propagates, but the state has already been flipped to authenticated.)

**Recommended fix:** On login failure, do not resurrect a persisted session. Set `status: 'unauthenticated'` (or `error`) and surface the failure. A persisted session should only be adopted during `initializeAuth()` bootstrap, not as a fallback for an explicit login attempt that just failed.

### P2-1 — `backendAuthenticated` / NIP-98 "ready" set without any verified backend round-trip
- **Severity:** P2
- **Category:** fake-completion
- **File:** `web/src/lib/stores/auth.svelte.js:435` and `:99-108`

```js
// configureBackendAuth()
if (supportsDirectNip98Auth(systemInfo)) {
  installDirectNip98Provider(api);
  updateAuthState({ ...compatibilityPatch({ restNip98Advertised: true, restNip98Ready: true }), error: null });
  return { method: 'nip98', pubkey };
}
```
```js
function compatibilityPatch({ restNip98Advertised = false, restNip98Ready = false, restNip98LastError = null } = {}) {
  return {
    compatibility: { restNip98Advertised, restNip98Ready, restNip98LastError },
    backendAuthenticated: restNip98Ready,
    directNip98Ready: restNip98Ready
  };
}
```

**Evidence / why not production-ready:** `restNip98Ready` (and therefore `backendAuthenticated` and `directNip98Ready`) is set to `true` merely because the discovered system info *advertises* support and a header-provider callback was installed. No signed request is ever sent and no server response is validated. `AuthGuard.svelte:28-30` and `route-access.js:99-101` gate REST-compatibility routes (e.g. `/orgs`) on exactly this flag, so the UI grants "backend authenticated" access before the backend has authenticated anything. If the backend actually rejects the NIP-98 header, the user still passes the guard and only discovers the failure mid-request.

**Recommended fix:** Treat "ready" as *provisional* until a real signed probe succeeds (e.g. a lightweight authenticated GET), then flip `restNip98Ready`. Keep `restNip98Advertised` separate from `restNip98Ready` and only set the latter on an observed 2xx.

### P2-2 — Persisted NIP-07 identity accepted at bootstrap without verifying the signer controls it
- **Severity:** P2
- **Category:** security (defense-in-depth / correctness)
- **File:** `web/src/lib/stores/auth.svelte.js:540-579` (`initializeAuth()`)

```js
const persisted = loadPersistedSession();
...
const supportsMethod =
  (persisted.authMethod === 'nip46' && nip46Available) ||
  (persisted.authMethod !== 'nip46' && extensionAvailable);

if (supportsMethod) {
  // (nip46 path reconnects; nip07 path does NOT re-check the key)
  ...
  updateAuthState({
    status: 'authenticated',
    pubkey: persisted.pubkey,
    ...
  });
```

**Evidence / why not production-ready:** For NIP-07, bootstrap only checks that *some* extension exists (`extensionAvailable`); it never calls `getPublicKey()` to confirm the extension still controls `persisted.pubkey`. Because the session lives in mutable `localStorage`, a tampered/stale entry makes the UI present a different identity than the connected signer. Not a server-side bypass (writes are re-signed by the actual extension), but the dashboard will display the wrong pubkey/profile and attribute actions to an identity the signer may not hold, until the first signature mismatch surfaces.

**Recommended fix:** During bootstrap, call `getNip07PublicKey()` and only adopt the persisted session if it equals `persisted.pubkey`; otherwise clear the session and fall through to unauthenticated.

### P2-3 — NIP-46 connect does not bind the returned pubkey to the session, and silently falls back to a NIP-07 signer
- **Severity:** P2
- **Category:** security (defense-in-depth / correctness)
- **File:** `web/src/lib/nostr/nip46-session.js:5-11, 38-46`

```js
function getProviderSigner(provider) {
  if (provider && typeof provider.signEvent === 'function') return provider;
  if (typeof window !== 'undefined' && window?.nostr && typeof window.nostr.signEvent === 'function') {
    return window.nostr;              // silent fallback to top-level NIP-07
  }
  return null;
}
...
let pubkey = null;
if (typeof provider.getPublicKey === 'function') {
  pubkey = await provider.getPublicKey();
} else if (typeof window !== 'undefined' && window?.nostr && ...) {
  pubkey = await window.nostr.getPublicKey();
}
if (!isValidHexPubkey(pubkey)) throw new Error('NIP-46 signer did not provide a valid public key');
```

**Evidence / why not production-ready:** The connected pubkey is only *format*-checked (`isValidHexPubkey`) — it is never compared against the signer pubkey encoded in the parsed connect URI (`session`). Combined with `getProviderSigner`/`getPublicKey` falling back to the top-level `window.nostr`, a "NIP-46 session" can be reported as connected while identity and signatures actually come from an unrelated NIP-07 extension. The app cannot distinguish "connected to the requested remote signer" from "silently using whatever local signer happens to exist."

**Recommended fix:** After connect, compare the resolved pubkey to the expected signer pubkey from the connect URI and reject on mismatch. Remove the implicit `window.nostr` fallback from the NIP-46 path (or gate it behind an explicit, logged decision), so a NIP-46 session only ever uses the NIP-46 provider.

### P2-4 — Route RBAC is empty and authorization config is sourced from mutable browser globals in production
- **Severity:** P2
- **Category:** security (defense-in-depth) / debt
- **File:** `web/src/lib/auth/route-access.js:18-43, 99-101`

```js
// Route-level RBAC hooks. Empty arrays mean "any authenticated user".
const ROUTE_ROLE_REQUIREMENTS = {};
...
function getRoleRequirements() {
  const overrides = typeof window !== 'undefined' ? window.__BAHIA_E2E_ROUTE_ROLE_REQUIREMENTS : null;
  if (!overrides || typeof overrides !== 'object') return ROUTE_ROLE_REQUIREMENTS;
  return { ...ROUTE_ROLE_REQUIREMENTS, ...overrides };
}
function getCompatibilityRequirements() {
  const overrides = typeof window !== 'undefined' ? window.__BAHIA_E2E_ROUTE_COMPAT_REQUIREMENTS : null;
  ...
}
```

**Evidence / why not production-ready:** `ROUTE_ROLE_REQUIREMENTS` is `{}`, so every protected prefix resolves to "any authenticated user" (`canAccessRoute` returns `roleAuthorized: true` whenever `requiredRoles.length === 0`). There is no client-side role differentiation for any route. Separately, both role and REST-compatibility requirements are merged from `window.__BAHIA_E2E_*` globals **unconditionally** — these E2E test hooks are live in production builds, so page-level script can weaken the compatibility gate (e.g. disable the `/orgs` requirement). This is UI-only (server contracts remain the real gate), but shipping test-only override hooks into production and having a completely empty RBAC map is a latent defect and misleading configuration surface.

**Recommended fix:** Compile the `window.__BAHIA_E2E_*` overrides out of production builds (guard on `import.meta.env.DEV` / a test flag). If per-route roles are intended, populate `ROUTE_ROLE_REQUIREMENTS`; if not, document that route protection is authentication-only so the empty map is not mistaken for an unfinished feature.

### P2-5 — Security rescan failures are swallowed to the console with no user-visible outcome
- **Severity:** P2
- **Category:** reliability / observability
- **Files:** `web/src/routes/security/[id]/+page.svelte:41-51`, `web/src/routes/security/+page.svelte:117-126`

```js
async function handleRescan() {
  if (!targetHash) return;
  rescanning = true;
  try {
    await rescanSecurityTarget(targetHash);
  } catch (err) {
    console.error('Rescan failed:', err);   // only signal to the user
  } finally {
    rescanning = false;
  }
}
```

**Evidence / why not production-ready:** These buttons trigger a real backend rescan action. On failure the only feedback is `console.error`; the spinner clears and the UI returns to idle, making a failed rescan indistinguishable from a successful one. For a *security* rescan surface this is a meaningful trust/observability gap — an operator can believe a rescan ran when it errored.

**Recommended fix:** Surface failures via the existing toast system (an error toast / inline error state) and a success confirmation, matching the pattern used elsewhere (e.g. `VoiceStudio` sets `errorMessage`).

### P2-6 — Repository fetch rejection is converted into a "success" returning stale data
- **Severity:** P2
- **Category:** reliability
- **File:** `web/src/lib/stores/repositories.svelte.js:127-135`

```js
} catch (err) {
  if (meta.requestSeq === nextSeq) {
    error.value = err?.message || 'Failed to load repositories';
  }
  return repositories;   // resolves with existing (possibly empty/stale) list
}
```

**Evidence / why not production-ready:** A rejected `fetchRepositories()` resolves the promise with the previous `repositories` array. Callers that `await loadRepositories()` cannot distinguish a fresh successful load from a silent fallback to stale state; `error.value` is set but the return value implies success. Callers that don't read `error.value` will render stale data as current.

**Recommended fix:** Re-throw (or return a discriminated result) so awaiters can react to failure, while keeping `error.value` for reactive consumers. At minimum, document that the return value is best-effort and callers must check `error.value`.

### P3-1 — Dead components from an abandoned rewrite (one contains a placeholder stub)
- **Severity:** P3
- **Category:** debt
- **Files:** `web/src/lib/components/VoiceStudio.svelte`, `web/src/lib/components/souls/MemoryConfig.svelte`

**Evidence / why not production-ready:** The soul routes (`routes/souls/new/+page.svelte`, `routes/souls/[id]/+page.svelte`) import `AvatarStudio`, `PersonalityBuilder`, `VoiceStudio` from `$lib/components/souls/…` but import `MemoryConfig` from the top-level `$lib/components/MemoryConfig.svelte`. A repo-wide import search confirms:
- `components/VoiceStudio.svelte` (a thin wrapper re-exporting `./souls/VoiceStudio.svelte`) has **zero importers**.
- `components/souls/MemoryConfig.svelte` has **zero importers**, and it is the file containing the `Reindex placeholder` stub (`souls/MemoryConfig.svelte:83-85`: "Reindex will become an event-driven runtime-control action; no polling or REST is used here."). The active top-level `MemoryConfig.svelte` is the one routes use.

These duplicated old/new components can be edited by mistake and drift from the live versions (classic "two code paths that disagree").

**Recommended fix:** Delete the unused `components/VoiceStudio.svelte` and `components/souls/MemoryConfig.svelte`, or, if `souls/MemoryConfig.svelte` was meant to be the live one, switch the route imports and retire the top-level copy. Consolidate on one component per studio.

### P3-2 — Silent catch blocks in cache and event projection hide operational failures
- **Severity:** P3
- **Category:** observability
- **Files:** `web/src/lib/stores/collections/indexeddb-cache.js:35-40, 69-78, 84-100, 105-119`; `web/src/lib/stores/collections/sbom.svelte.js:147-152`

```js
// indexeddb-cache.js — read failures become an empty cache, indistinguishable from a cache miss
} catch { return []; }
} catch { return false; }
```
```js
// sbom.svelte.js — malformed relay content silently projected as empty object
let content = {};
try { content = JSON.parse(event.content || '{}'); } catch { /* ignore */ }
```

**Evidence / why not production-ready:** IndexedDB open/read/write/delete errors and malformed SBOM event JSON are discarded with no logging. A failed cache read is indistinguishable from a valid empty cache, and corrupt relay data is rendered as a valid-but-empty SBOM. These are graceful-degradation choices, but with zero telemetry they will mask real relay/browser storage problems in production.

**Recommended fix:** Keep the fallbacks but log via the app's warn channel (as the repository store already does with `console.warn('[repositories] …')`), and for SBOM, mark the projected record as `parseError` so the UI can distinguish "empty" from "unparseable."

### P3-3 — `ensureRepositoryConnection()` is an awaited no-op that reads as a guarantee
- **Severity:** P3
- **Category:** debt
- **File:** `web/src/lib/stores/repositories.svelte.js:84-88`

```js
export async function ensureRepositoryConnection() {
  // Do NOT call nostr.connect() here. ...
}
```

**Evidence / why not production-ready:** `loadRepositories()` does `await ensureRepositoryConnection()` as if it verifies connection readiness, but the body is empty (with a valid rationale comment about not clobbering the singleton relay list). The name over-promises: callers may assume connectivity is guaranteed after it resolves. This is low-risk but a maintenance trap.

**Recommended fix:** Rename to reflect reality (e.g. remove it, or make it actually assert the singleton is connected/bootstrapped without mutating its relay list) so future edits don't "fix" the empty body by adding a harmful `connect()`.

**Overall:** The Nostr transport core, Go discovery/client packages, and the bulk of the stores are real and reasonably well-built — most of what looks like "fake completion" is either intentional REST deprecation or discovery-driven config. The concrete production defects cluster in two places: (1) the **auth store**, which repeatedly asserts authenticated/backend-ready state that was never verified, and (2) a small number of **stores/routes that swallow failures or fabricate load-completion** (CI enrichment, repository fetch fallback, security rescan). Fixing P1-1, P1-2, and the P2 auth trio would remove the most misleading behavior before production.
