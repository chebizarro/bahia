# Investigation: Fake Nostr Implementations Across Bahia Routes and Control Surfaces

## Summary
Bahia has a substantial real Nostr foundation, especially for read-model bootstrap and relay subscriptions, but many control surfaces still preserve REST/CRUD/RPC semantics either as direct HTTP, REST-to-Nostr bridges, or Nostr request/result facades. The current `/orgs/**` routes are not direct browser REST calls; they are encrypted Nostr request/result operations over backend domain CRUD repositories, while `/ml` is the clearest current browser REST-to-Nostr bridge and `/continuity` is direct HTTP.

## Symptoms
- Some Bahia app routes appear Nostr-based but call REST endpoints directly.
- The `orgs` route is suspected to force REST-like semantics over Nostr pub/sub.
- The codebase may contain hand-rolled Nostr primitives and wrappers for events, websockets, signers, subscriptions, and relay interactions.
- Bahia should be Nostr-first: event-driven REQ/EVENT/EOSE/OK/CLOSED/AUTH flows with scoped subscriptions and validation.

## Background / Prior Research
No external research performed yet. Initial triage indicates this is primarily an in-workspace architecture audit; git archaeology may be added if implementation history becomes relevant.

## Investigator Findings
### Codex Deep Audit — 2026-06-02

#### Executive findings

- **H1 — `web/src/routes/orgs/**` as direct REST facade:** **Disproved for current browser route callsites.** The org pages import `web/src/lib/stores/orgs.svelte.js`, which uses encrypted Nostr request/result events (`kind 5980` request, `kind 7980` result), not `web/src/lib/api/client.js` REST methods. Evidence: `web/src/lib/stores/orgs.svelte.js:1-3`, `web/src/lib/stores/orgs.svelte.js:36-45`, `web/src/lib/stores/orgs.svelte.js:70-143`.
- **H1 — orgs as fake-Nostr/domain CRUD facade:** **Proved as a backend semantic seam.** The encrypted org operations are operation-string RPC over Nostr (`orgs.list`, `orgs.create`, etc.) and backend handlers directly call org/member/invite repositories. The backend comment explicitly says these handlers adapt “sensitive REST-backed domains” to encrypted signer-first request/result operations. Evidence: `internal/controlplane/encrypted_domain_handlers.go:19-36`, `internal/controlplane/encrypted_domain_handlers.go:84-95`, `internal/controlplane/encrypted_domain_handlers.go:127-233`.
- **H2 — route/control surface transport:** **Mixed overall.** Most current Svelte routes consume Nostr read-model stores and publish Nostr commands, but several surfaces still use REST compatibility or REST-to-Nostr bridges. ML is the clearest route-level REST-to-Nostr bridge; Continuity is direct HTTP; Blossom is HTTP-native and not fake; orgs/payments/notifications/service-secrets/deployment logs are encrypted request/result rather than REST callsites.
- **H3 — frontend helper semantics:** **Proved.** Frontend helpers implement publish-then-await-result and encrypted request/result flows. They verify publish acceptance, use narrow correlation filters, dedupe, and handle `CLOSED`/auth closures, but completion still resolves a Promise on the first correlated result event and, in encrypted flows, defaults to timeout-based terminal failure. Evidence: `web/src/lib/stores/public-controlplane.svelte.js:25-31`, `web/src/lib/nostr/controlplane-requests.js:70-195`, `web/src/lib/nostr/encrypted-controlplane.js:159-286`.
- **H4 — backend/internal seams:** **Proved in part.** Core backend reactor/FIPS paths are largely EOSE/CLOSED/AUTH-aware, but drift-prone kind duplication, legacy/deprecated subscription APIs, REST-to-Nostr ML ingress, encrypted operation dispatch, and bootstrap timeout seams remain. Evidence: `internal/kinds/kinds.go:1-8`, `internal/adapters/nostr/catalog.go:14-128`, `internal/controlplane/reactor.go:29-134`, `internal/controlplane/ml_command_publisher.go:13-24`, `internal/adapters/nostr/bootstrapper.go:256-277`.

#### Classification key

- **Real Nostr-native:** route/control surface uses scoped relay subscriptions, Nostr events, EOSE/live handling, event validation/dedupe, and publish OK checks where applicable.
- **REST-backed:** browser or control surface directly calls HTTP endpoints for the behavior being presented.
- **Mixed REST-to-Nostr bridge:** HTTP ingress publishes Nostr commands or route mixes REST actions with Nostr read models/commands.
- **Nostr request/result facade:** uses Nostr transport, but semantically wraps operation strings and terminal result waits rather than exposing durable domain event semantics.
- **HTTP-native-but-not-fake:** HTTP is the expected protocol, or the UI does not claim Nostr-native behavior for that operation.
- **Unknown/follow-up:** not enough code path evidence in this pass.

#### Orgs chain: evidence and conclusion

Observed browser chain:

```text
web/src/routes/orgs/**
  → web/src/lib/stores/orgs.svelte.js
  → web/src/lib/nostr/encrypted-controlplane.js requestEncryptedResult()
  → kind 5980 encrypted request / kind 7980 encrypted result
  → internal/controlplane/encrypted_transport.go
  → internal/controlplane/encrypted_domain_handlers.go repository operations
```

Key frontend evidence:

- Org store imports encrypted Nostr transport and system discovery, not the REST API client: `web/src/lib/stores/orgs.svelte.js:1-3`.
- It refuses to run unless encrypted Nostr requests are advertised: `web/src/lib/stores/orgs.svelte.js:29-41`.
- It sends operation strings via `requestEncryptedResult()` with `['domain','orgs']` tag: `web/src/lib/stores/orgs.svelte.js:36-45`.
- It serializes startup requests because signer bridges are flaky: `web/src/lib/stores/orgs.svelte.js:70-76`. This is a presentation-neutral but architecture-relevant smell: org overview is two sequential request/result operations.
- CRUD-style org operations are string commands: `orgs.detail`, `orgs.create`, `orgs.delete`, `orgs.accept_invite`, `orgs.create_invite`, `orgs.update_member_role`, `orgs.remove_member` (`web/src/lib/stores/orgs.svelte.js:88-143`).

Key backend evidence:

- Encrypted domain handler operation constants are string RPC names: `internal/controlplane/encrypted_domain_handlers.go:19-30`.
- The handler comment explicitly states the adapter role: “sensitive REST-backed domains” → encrypted request/result operations (`internal/controlplane/encrypted_domain_handlers.go:34-36`).
- `Register()` maps each operation string to handler methods: `internal/controlplane/encrypted_domain_handlers.go:84-95`.
- Org list/details/create read and mutate repositories directly (`members.ListByPubkey`, `orgs.GetByID`, `members.ListByOrg`, `orgs.Create`, `members.Add`) rather than consuming durable org-domain Nostr events: `internal/controlplane/encrypted_domain_handlers.go:127-233`.
- Legacy REST org routes are still mounted: `internal/api/router/router.go:232-237`, `internal/api/router/router.go:386-397`.

Conclusion: **Current org routes are not direct REST-backed frontend facades, but they are Nostr-wrapped domain CRUD.** The Nostr transport is real enough to sign, encrypt, validate, dedupe, subscribe, and publish OK-checked results; the domain semantics are not Nostr-native org event semantics.

#### Frontend Nostr helper seams

1. **Public commands publish then await one terminal result.** `publishCommand()` calls `publishRequest()` and then `awaitResult()` before returning (`web/src/lib/stores/public-controlplane.svelte.js:25-31`). This affects services, environments, deployments, LLM, artifacts, packages, policies, backup, and worker commands.

2. **Publish OK is checked, but terminal flow is request/result.** `publishRequest()` signs, publishes, filters accepted relays, and rejects if no relay accepted (`web/src/lib/nostr/controlplane-requests.js:70-95`). `awaitResult()` subscribes to `{ kinds, '#e': [requestEventId], authors: [servicePubkey] }`, dedupes, and resolves on the first correlated result (`web/src/lib/nostr/controlplane-requests.js:120-195`). It has `onClosed` handling, including auth closure, but no `onEose` path because the helper is waiting for a realtime terminal result.

3. **Encrypted private transport is request/result with default timeout.** Encrypted flow defines request/result kinds and a 15s timeout (`web/src/lib/nostr/encrypted-controlplane.js:5-9`). It publishes and requires accepted relays (`web/src/lib/nostr/encrypted-controlplane.js:138-156`), then subscribes to correlated result events with `#e`, `#p`, and author filters (`web/src/lib/nostr/encrypted-controlplane.js:159-239`). `requestEncryptedResult()` starts the result wait, publishes the request, awaits the result, and disconnects the ephemeral client (`web/src/lib/nostr/encrypted-controlplane.js:244-286`).

4. **Read-model bootstrap is closer to Nostr-native.** Dashboard bootstrap subscribes to read-model filters and tracks EOSE per connected relay before marking bootstrap complete; it keeps the subscription open for realtime updates (`web/src/lib/stores/controlplane/bootstrap.svelte.js:49-84`, `web/src/lib/stores/controlplane/bootstrap.svelte.js:91-139`).

5. **EOSE query helper supports timeout and partial fallback.** `queryUntilEose()` can reject on a timeout while waiting for EOSE (`web/src/lib/nostr/pool-query.js:1-87`). Soul Factory helpers wrap that with `queryUntilEoseOrPartial()` and may return partial or empty event sets on incomplete EOSE (`web/src/lib/nostr/subscriptions.js:91-109`), then use those helpers for templates/souls/drafts/runtime capabilities (`web/src/lib/nostr/subscriptions.js:116-160`). This is not REST-backed, but it weakens strict EOSE semantics.

6. **Provisioning progress subscription lacks close/EOSE/auth callbacks.** `subscribeToProvisioningProgress()` listens for status/result with `#e` correlation but only provides `onEvent` (`web/src/lib/nostr/subscriptions.js:166-177`). It does not handle `CLOSED`, `AUTH`, or `EOSE` at this seam.

7. **Hardcoded browser default relay remains.** The frontend singleton falls back to `wss://bahia.sharegap.net/relay` (`web/src/lib/nostr/subscriptions.js:8-10`). The settings route can override this, but the production-path default is a hardcoded relay URL.

#### Backend/internal Nostr seams

1. **Kind constants are not single-sourced despite a single-source claim.** `internal/kinds/kinds.go` says all packages should import kind constants from there (`internal/kinds/kinds.go:1-8`), but `internal/adapters/nostr/catalog.go` defines a large parallel set (`internal/adapters/nostr/catalog.go:14-128`), `internal/controlplane/reactor.go` aliases many catalog constants and hardcodes read-model kinds (`internal/controlplane/reactor.go:29-134`), `internal/controlplane/ml_command_publisher.go` separately hardcodes ML read-model kinds (`internal/controlplane/ml_command_publisher.go:13-24`), and encrypted request/result kinds are duplicated in both frontend and backend (`web/src/lib/nostr/encrypted-controlplane.js:5-9`, `internal/controlplane/encrypted_transport.go:16-21`). This is drift-prone even where values currently match.

2. **Deprecated subscription API still exists.** `RelayPool.SubscribeAll()` remains public and is explicitly deprecated in favor of `SubscribeAllWithEOSE()` (`internal/adapters/nostr/relay_pool.go:457-462` from local search). The inspected reactor/bootstrap paths use EOSE-aware subscriptions, but the deprecated API is still available for new drift.

3. **Encrypted backend transport validates events but dispatches operation strings.** `EncryptedRequestTransport.Run()` subscribes with kind, routing tag, `since`, and service `p` tag filters (`internal/controlplane/encrypted_transport.go:213-239`). `HandleEvent()` checks signature, dedupes, validates routing/auth, decrypts, verifies requester pubkey, dispatches by `envelope.Operation`, then publishes a correlated encrypted result (`internal/controlplane/encrypted_transport.go:243-302`). This is a solid Nostr transport seam wrapped around RPC-like domain operations.

4. **Encrypted result publish checks relay acceptance count but loses per-relay OK detail at this abstraction.** `PublishEncryptedResult()` signs, calls `publisher.Publish()`, and rejects zero accepted relays (`internal/controlplane/encrypted_transport.go:113-169`). Per-relay OK message handling appears lower in the relay pool; the encrypted responder only sees accepted count/error.

5. **ML REST ingress publishes Nostr commands.** Router labels ML writes as “write compatibility actions publish Nostr commands” (`internal/api/router/router.go:424-431`). The frontend ML page uses REST `api.importMLModel()`/`api.deployMLEndpoint()` (`web/src/routes/ml/+page.svelte:114-123`, `web/src/routes/ml/+page.svelte:186-193`). The publisher signs Nostr request events and fails if no relay accepts (`internal/controlplane/ml_command_publisher.go:127-151`). This is intentional compatibility, but it is not signer-first browser control.

6. **Bootstrapper waits for EOSE with a timer.** `Bootstrapper.runGroup()` subscribes with EOSE, then returns an error when `timer.C` fires before EOSE (`internal/adapters/nostr/bootstrapper.go:256-277`). This may be a health/safety timeout, but it is also a completion-detection timer around EOSE and conflicts with the strict “no timeout-based completion” rule unless explicitly justified.

7. **Core reactor/FIPS paths look stronger than the fake seams.** The backend control-plane reactor aliases canonical catalog request/status/result kinds and notes `311xx` publisher kinds are deprecated (`internal/controlplane/reactor.go:29-32`). Explore results found EOSE/CLOSED/AUTH handling in reactor and FIPS subscribers; no missing OK/CLOSED/AUTH/EOSE finding was proven in those core paths during this pass.

8. **PSTF evidence overstates production readiness for AI/ML.** `AI_FABRIC_HF_VLLM_DEPLOYMENT` status is `verified_d4_harness` (`pstf/features/AI_FABRIC_HF_VLLM_DEPLOYMENT/test_matrix.json:1-4`), but the verification report says the path uses local fakes/mocks only and no real Hugging Face, vLLM, GPU, OCI, or relay access (`pstf/features/AI_FABRIC_HF_VLLM_DEPLOYMENT/verification_report.md:3-17`) and confidence is only high for the fake/no-network path (`pstf/features/AI_FABRIC_HF_VLLM_DEPLOYMENT/verification_report.md:43-46`). Related signer-first protocol PSTF remains a placeholder with no product code implemented (`pstf/features/AI_FABRIC_SIGNER_FIRST_PROTOCOL/verification_report.md:3-15`).

#### Overall conclusion

The strongest finding is not that Bahia’s current web app is simply REST pretending to be Nostr. The current state is more nuanced:

- The shared dashboard/read-model architecture is substantially Nostr-based and uses EOSE/live subscriptions.
- Public control-plane mutations are Nostr-published and OK-checked, but the browser helpers commonly turn them into publish-and-await-result Promise flows.
- Sensitive surfaces moved off direct browser REST to encrypted Nostr request/result, but backend handlers explicitly adapt REST-backed/domain CRUD repositories and do not expose durable domain-specific Nostr event semantics.
- ML remains the clearest user-facing REST-to-Nostr bridge in the current routes.
- Continuity is direct HTTP in the inspected route.
- Blossom is HTTP-native and should not be counted as fake Nostr.
- Backend core Nostr handling is stronger than the frontend helper seams, but kind duplication, deprecated APIs, bootstrap timeout completion, and stale PSTF claims are real production-readiness risks.

## Root Cause
Bahia’s root problem is semantic drift, not absence of Nostr infrastructure. The repo contains real Nostr transport, publish OK checks, scoped subscriptions, EOSE-aware read-model bootstrap, inbound validation, dedupe, and CLOSED/auth handling in several seams. However, many user-facing workflows still model work as HTTP/CRUD/RPC:

1. **Direct REST facades** remain where routes call HTTP for the control surface, e.g. continuity loads `/api/continuity/status` and `/api/continuity/topology` via `web/src/routes/continuity/+page.ts:1-21` and `web/src/lib/api/continuity.ts:5-32`.
2. **REST-to-Nostr bridges** remain where browser REST calls submit work and backend handlers publish Nostr commands, e.g. ML calls `api.importMLModel()` and `api.deployMLEndpoint()` in `web/src/routes/ml/+page.svelte:114-123` and `web/src/routes/ml/+page.svelte:186-193`, then backend ML handlers publish async Nostr command receipts.
3. **Nostr request/result facades** use real signed/encrypted Nostr transport but wrap domain operations as operation-string RPC with terminal Promise waits, e.g. orgs call `requestEncryptedResult()` with `orgs.*` operation names in `web/src/lib/stores/orgs.svelte.js:36-143`, while `internal/controlplane/encrypted_domain_handlers.go:19-36` explicitly adapts “sensitive REST-backed domains” to encrypted request/result operations and maps those operation strings at `internal/controlplane/encrypted_domain_handlers.go:84-95`.
4. **Protocol weakening helpers** convert strict event-stream behavior into REST-like completion or degraded success: `awaitResult()` resolves on the first correlated event and optional timer in `web/src/lib/nostr/controlplane-requests.js:117-195`; encrypted result waits default to a 15s timeout and settle on first correlated result in `web/src/lib/nostr/encrypted-controlplane.js:5-9` and `web/src/lib/nostr/encrypted-controlplane.js:159-286`; partial EOSE helpers can return partial or empty event sets as normal-looking results in `web/src/lib/nostr/subscriptions.js:91-160`.
5. **Architecture drift seams** make protocol correctness hard to enforce: duplicated kind constants despite single-source intent, deprecated non-EOSE subscription APIs still available, bootstrap completion timers around EOSE, and stale PSTF artifacts that overstate readiness.

The correct final classification is therefore nuanced: Bahia is not merely REST pretending to be Nostr, but it is still carrying REST-programmer semantics through compatibility endpoints and Nostr RPC facades instead of consistently modeling product behavior as durable Nostr event streams.

## Recommendations
1. **Create and enforce a route/control-surface transport matrix.** For every web route and backend surface, classify it as `nostr_native`, `nostr_request_result_facade`, `rest_to_nostr_bridge`, `rest_compatibility`, or `http_native`. Start from this report’s table and make it a PSTF artifact for Nostr audit parity.
2. **Fix org semantics before treating orgs as Nostr-native.** Target `web/src/lib/stores/orgs.svelte.js`, `web/src/lib/nostr/encrypted-controlplane.js`, `internal/controlplane/encrypted_domain_handlers.go`, and `internal/controlplane/encrypted_transport.go`. Keep encrypted transport for private payloads, but replace opaque `orgs.*` CRUD operation strings with durable org-domain event kinds and read-model projections, or explicitly document the current path as encrypted RPC compatibility.
3. **Decide ML ingress policy.** Target `web/src/routes/ml/+page.svelte`, `web/src/lib/api/client.js`, `internal/api/handlers/ml.go`, and `internal/controlplane/ml_command_publisher.go`. Either label ML as REST compatibility ingress or move browser actions to signer-first Nostr command publishing like the cleaner LLM/packages/workers paths.
4. **Standardize request/result lifecycle semantics.** Target `web/src/lib/stores/public-controlplane.svelte.js`, `web/src/lib/nostr/controlplane-requests.js`, `web/src/lib/nostr/dns-controlplane.js`, `web/src/lib/nostr/encrypted-controlplane.js`, `pkg/client/operator_nostr.go`, and `internal/controlplane/*_command_publisher.go`. Require: subscribe result/status stream before publish where feasible, verify per-relay OK or duplicate, distinguish status from terminal result kinds, reject CLOSED/AUTH distinctly, and refresh durable read models through EOSE-aware subscriptions.
5. **Remove normal-looking partial EOSE success for critical state.** Target `web/src/lib/nostr/subscriptions.js`, `web/src/lib/nostr/branches.js`, `web/src/lib/nostr/repositories.js`, and Soul Factory callsites. If partial history is accepted, return an explicit degraded result object with relay status, never a plain list indistinguishable from complete history.
6. **Single-source Nostr kinds.** Target `internal/kinds/kinds.go`, `internal/adapters/nostr/catalog.go`, `internal/adapters/nostr/publisher.go`, `internal/controlplane/ml_command_publisher.go`, `web/src/lib/nostr/kinds.js`, and `web/src/lib/nostr/bahia-kinds.js`. Generate frontend/backend constants from one catalog and block new hand-defined kind constants outside approved generated files.
7. **Retire deprecated or unsafe protocol APIs.** Target `internal/adapters/nostr/relay_pool.go`, `internal/adapters/nostr/publisher.go`, and any callers of deprecated subscription paths. EOSE/CLOSED/AUTH-aware subscription APIs should be the only production path.
8. **Correct stale PSTF evidence.** Update Nostr audit parity and AI/ML PSTF artifacts so verification does not claim production readiness from fake-only harnesses or outdated subscriber/reactor ownership assumptions.

## Preventive Measures
- Add PSTF acceptance criteria requiring every route/control surface to declare its transport class and forbidding signer-first routes from importing `$lib/api/client.js` for command submission.
- Add deterministic tests that map each route class to expected behavior: direct REST compatibility returns explicit compatibility receipts; Nostr-native routes publish signed events, verify OK, handle CLOSED/AUTH, and refresh via EOSE-aware subscriptions.
- Add tests for public and encrypted request/result helpers proving terminal completion uses result kinds only, status events cannot satisfy completion, auth/CLOSED failures reject explicitly, and publish failure/partial relay acceptance is surfaced.
- Add EOSE tests that fail when critical read helpers convert incomplete history into plain empty or partial success.
- Add a generated-kind consistency check comparing backend and frontend kind constants, and fail CI on ad hoc kind definitions outside approved generated/catalog modules.
- Add PSTF verification gates that distinguish real production integrations from mock/fake harnesses; fake-only verification must create Beads defects rather than marking production readiness complete.
- Preserve wording discipline in docs and UI: call encrypted private flows “encrypted request/result compatibility” unless the domain behavior is actually modeled as durable Nostr events and projections; call REST-to-Nostr endpoints “compatibility ingress,” not signer-first browser Nostr.
