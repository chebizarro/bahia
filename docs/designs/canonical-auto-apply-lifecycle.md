# Canonical auto-apply lifecycle (`bahia-4f10q.2`)

Status: the route-free, Bahia-managed Docker auto-apply path is enabled behind `reconcile.enabled` and `direct_runtime_actions.enabled`. Its signed tool request/approval extension is enabled only for the bounded local-Docker path below. The LLM extension admits encrypted releases and observable external-API gateway routes behind `llm.enabled`; its remaining effects fail closed as described below. This is not permission to route SQL-backed `RuntimeLifecycleService` through the reconciler.

## Authority and bounded input contract

The executor reads the daemon's local Nostr event store, not PostgreSQL. It requires a service-signed winning service state (30900) with a complete, recomputed `DesiredServiceSpec`, the matching service-signed deployment-intent registry record, service/environment and artifact registry records, and an exact operator-signed deployment decision event. A service-signed, accepted 30315 status referencing that decision event is the durable proof that the normal intent processor authorized it. For an unprotected create/rollback, the intent registry's `nostr_event_id` must identify that event. For an explicit approval, the accepted status must reference an operator `deployment/approve` event naming the same deployment intent. The state/intent/spec identities and hashes must agree. A missing, superseded, deleted, forged or unlinked input is a no-effect outcome. Once a receipt has admitted a decision, an observed stale winner produces a signed fresh-decision-required checkpoint; without an admitted receipt there is no decision snapshot to report.

The decision snapshot binds the exact decision event ID and coordinate/actor; the winning service, service-state, deployment-intent, environment and artifact event IDs; the release/artifact event ID; the desired spec and deployment-unit target; and each required secret ID, environment-variable binding, Signet credential ID and version. A route event ID/revision field exists, but the currently supported path requires no public route. Runtime-release bindings and canary release promotions have no replay-safe effect adapter yet and are refused, rather than being inferred from an artifact or SQL row. The specific signed events read are compared again under the fence before effect. Latest-wins and observed conflicts govern; no EOSE-fenced global membership or absence proof is claimed. EOSE is not absence.

Decision construction pins store-backed secret references in the signed desired spec, without fetching a value. It reads canonical secret metadata and uses Signet `Inspect` to verify the active version and tenant/service label. Those IDs and versions contribute to the desired hash. The executor requires every desired secret to have such a pin, checks the current canonical reference, then calls the Signet-backed `SecretStore.ResolveAll` at use time (`credential/deliver` with `expected_version`). A changed/revoked/missing version is `fresh_decision_required`, not a silent rotation. Values exist only in apply-scoped memory and are dropped/zeroized afterward. Old desired specs without pins remain observe-only.

The Docker adapter accepts only an auto-apply, Bahia-managed deployment unit and refuses adopted runtime configuration or plaintext secret fields. It resolves the runtime from the signed service/environment/unit values, observes the exact managed container and `bahia.desired_hash`, and passes the signed spec and resolved secrets to the desired-state applier. Compose, public-route, canary, and runtime-release effects remain fail closed. The bounded Docker tool extension is described below; `bahia-4f10q.2.2` owns LLM effects.

## Tool request and approval extension (`bahia-4f10q.2.1`)

The enabled subset consumes an exact fleet-operator-signed `30900` `tool/request` with a UUIDv7 request ID, service/environment target, explicit pinned package manager/name/version list, and reason. The operator-signed `tool/approval-response` at `tool-approval:<request-id>` must cite **that request event ID**; a matching SQL row or unsigned MCP transport identity is not authority. The ordinary intent processor publishes checked service-signed accepted `30315` statuses for both signed events via `PublishBeforeCommit`. Their historical target/quorum relay OKs are retained as outbox delivery proofs. The controller stages an immutable, secret-value-free decision snapshot before publishing the approval acceptance, and never dispatches until both exact acceptance proofs exist. A restart scans staged decisions after local catch-up. Denials create a signed, durable `refused` 30315 checkpoint and no external effect.

The tool snapshot additionally binds the request event ID/actor/coordinate, the approval event ID/coordinate, every service/state/deployment-intent/environment/artifact winner read by the Docker base source, the approved target spec, each desired Signet credential ID/version, and the latest observed signed fleet denylist winner IDs. Package resolution is limited to pinned `apt`, `pip`, `npm`, and `cargo` names; a denied package, malformed input, stale winner, or moved credential version requires a fresh decision. This does not claim that EOSE proves no other denylist entries exist. A new observed winner before effect invalidates the admitted snapshot.

Build and deploy are separate receipt families sharing the per-environment filesystem fence. Build uses a deterministic toolset hash and local Docker image tag, confirms the hash-labeled image before completing its signed checkpoint, then deploy observes the exact managed container desired hash. A crash after a build/deploy effect but before checkpoint advances only after positive observation; ambiguous partial effects enter `recovery_required` and are **not retried**. A crash after checkpoint before outbox publish re-enqueues the original signed event. A terminal deploy receipt never redoes either effect. PostgreSQL is not read or written by this executor. Legacy ContextVM kind-5976 provisioning, unsigned MCP fabrication, non-Docker runtimes, public routes, and cross-host execution remain paused with `bahia-4f10q.2.1`; the old SQL tool coordinator is not started by the app.

## LLM release and external-API route extension (`bahia-4f10q.2.2`)

The enabled subset accepts only exact fleet-operator-signed, locally observed `30900` LLM lifecycle requests with UUIDv7 idempotency keys. `release-register` stages one immutable service-signed encrypted `32015` release event in the local outbox control record. It publishes that same event through `PublishBeforeCommit` and verifies the retained target/quorum relay-OK proof **before** the intent processor may report an accepted `30315`. Neither a SQL release row nor a route record is a release receipt. Replayed registration uses the admitted event and proof; it never re-encrypts a new event for the same release ID. The SQL LLM coordinator remains absent.

`deploy` and `rollback` stage a secret-value-free request snapshot in the local outbox before acceptance. The snapshot binds the exact signed request event, route and environment winners, encrypted release event and quorum proof, record `updated_at`/creation revision, gateway admin endpoint configuration revision, previous terminal route checkpoint, decision actor/coordinate/event, and required Signet secret IDs, credential IDs and versions. Protected environments wait for an exact signed `approve` or `reject` on the deployment-intent coordinate; a decision itself requires the request's exact accepted-status quorum proof. Approval selects a fresh snapshot at decision time, while rejection creates a signed `refused` `30315` checkpoint. An unapproved request has the processor's signed accepted-request status but **no external effect**. Execution requires historical quorum proofs for the exact request and, when protected, approval statuses. These accepted statuses have no NIP-40 expiry while a local effect receipt may need them for restart recovery; their per-requester/coordinate `d` tags remain replaceable. Latest-wins is limited to the specific locally observed signed events; observed conflict or moved secret version requires a fresh decision. No EOSE/absence claim is made.

For the supported external-API backend, the gateway's `GET` observation of a synced managed-config hash fences its idempotent `PUT`. The route effect runs under the same per-environment filesystem lock and `accepted` → `effect_started` → `effect_observed` → `terminal` local receipt/signed-30315 checkpoint sequence as Docker auto-apply. A process death after PUT but before checkpoint resumes only after positive gateway observation; missing/ambiguous state enters `recovery_required` and does not repeat PUT. An ambiguous or observed-but-not-terminal prior route effect blocks **all newer decisions for that route/environment**: a possibly in-flight old PUT cannot be allowed to overwrite a newer completed route after restart. A death after checkpoint before outbox admission re-enqueues the original signed checkpoint. Terminal or denied replay never invokes the gateway again. The previous terminal checkpoint forms a per-route/environment chain, so rollback does not rely on equal-second wall-clock ordering. PostgreSQL is not read or written for this lifecycle; route registry records are canonical local-store inputs and SQL is only a possible derived index.

The effect adapter deliberately refuses runtime-managed model launch/placement, mixed backend preferences, non-HTTPS external endpoints, literal gateway headers, backend health checks/headers, release/route metadata, and gateway admin auth tokens not represented by versioned Signet references. It also refuses absent gateway configuration; route registry mutations still need their existing SQL read model and are outside this DB-less lifecycle. Those remain `bahia-4f10q.2.2` follow-up work; no dormant SQL coordinator or fabricated transport-principal intent is enabled. The health gate remains warning-level for this bounded capability.

## Non-PostgreSQL effect fence and deployment precondition

`RuntimeApplyLock` uses per-environment advisory filesystem locks beside the durable outbox. Manual deploy/rollback/restart/stop, supervised recovery, and canonical Docker auto-apply share it. The lock is taken before selecting execution inputs and held through effect, observation and local receipt admission. A failed lock never falls back to a process-local mutex. PostgreSQL advisory locks are not an effect fence.

The deployment contract is **one active daemon per service identity**. A remote signer bunker authorizes exactly one client key; local signing requires a single daemon instance. This is the same precondition adopted for backup admission in `bahia-cd0wr`; Bahia adds no epoch or lease protocol. The filesystem lock and exclusive local outbox handle are same-host defense in depth. Cross-host coordination and an external actor concurrently mutating the same target are out of scope and prohibited by deployment policy.

## Receipt, checkpoint, relay delivery and crash replay

The executor stores a secret-value-free immutable decision snapshot in a durable outbox-side control record keyed by deployment intent ID **before** any external effect. Its phases are `accepted`, `effect_started`, `effect_observed`, and `terminal`, plus fail-closed `refused`, `superseded`, and `recovery_required`. Each phase stores the exact signed kind-30315 checkpoint event in the same local record before outbox admission. If the process dies between those writes, startup re-enqueues the *same* signed event; it never signs a replacement for the same phase. NIP-01 replacement timestamps use `max(now, previous+1)` and refuse a floor more than 30 seconds ahead. The outbox owns relay OK/quorum evidence and retries delivery; a failed quorum does not authorize another runtime apply.

On restart, after canonical local catch-up, the receipt runner first restores any missing checkpoint to the outbox. It resumes nonterminal receipts under the same effect fence. If the Docker managed container already runs the pinned desired hash, an `effect_started` receipt advances to observed/terminal without another apply. A missing or ambiguous resource after `effect_started` is `recovery_required`: the executor will **not** blindly repeat a potentially partial external effect. A checkpointed or terminal decision never repeats the effect. Before reporting terminal success, the executor rereads the bound winners; a changed winner records the old effect as superseded instead of claiming current convergence. PostgreSQL is only a best-effort derived index and is never consulted for execution or replay.

The workflow coordinator's production `auto_apply` dispatch is guarded: it invokes the canonical executor with lookup identities only, and legacy direct-run recovery is prohibited for auto-apply units. If canonical input/status has not arrived yet, the attempt fails closed; the local reconciler or receipt runner retries after catch-up. Unsupported effect types cannot fall through to Loom or the SQL-backed manual lifecycle. Manual user-initiated operations retain their separate behavior while sharing the filesystem fence.

## Verification and explicit limits

Deterministic tests cover crash after effect/before checkpoint, crash after checkpoint/before outbox admission, startup terminal checkpoint repair, each bound revision moving, Signet version mismatch at use time, signed local input selection without PostgreSQL, and same-host process exclusion. Architecture ratchets prevent wiring the SQL lifecycle into auto-remediation or introducing a PostgreSQL effect lock. The full quality gates are recorded with the task handoff.

This bounded set does **not** solve Compose multi-service/partial-project replay, public route provider steps, canary rollout, runtime-release binding execution, legacy ContextVM tool provisioning, or runtime-managed LLM provisioning. Those require their own revision-fenced step adapters and tests; until then the executor fails closed. It also does not claim that a local event cache proves absence across relays. A deployment lacking an exact accepted status or decision-time secret pin requires a fresh signed decision.
