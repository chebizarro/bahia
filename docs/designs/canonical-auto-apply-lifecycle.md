# Canonical auto-apply lifecycle (`bahia-4f10q.2`)

Status: implementation design; `auto_apply` remains suspended. This document does not authorize wiring `RuntimeLifecycleService` into the reconciler. Production canonical readers reject duplicate unit IDs, conflicting environment bindings, and embedded desired specs whose recomputed body hash or service/environment/artifact/unit identity differs from the signed service-state record. These read validations are not operator-intent authorization, secret-version binding, or an apply/replay fence.

## Current seam and invariant

`internal/app/app.go` passes `WithAutoRemediationDeployer(nil)`, so `internal/reconcile/reconciler.go` publishes drift without remediation. The SQL-backed `RuntimeLifecycleService` no longer implements the auto-remediation interface; an architecture test guards against reintroducing that entry point or changing the startup suspension without deliberately updating the ratchet. Its manual `deployDesiredState` path resolves service, environment, artifact, unit, effective secrets, and sibling plan via repositories; `EnvironmentPlanAssembler` can hydrate and persist a missing sibling; the external `ApplyDesiredState` occurs before `updateDesiredArtifact`, observation recording, and event publishing. Its environment lock is acquired only after most inputs are read. An absent or divergent PostgreSQL index can therefore choose a different effect than the signed `30900` state. Do not use the manual lifecycle as an automatic executor.

The authority for automatic repair is the current validated, service-authored local `30900` service-state record, not a SQL row, latest artifact lookup, or a new synthetic deployment intent. The existing operator-signed intent establishes desired state; automatic reconciliation may reassert exactly that state but must not choose a new target, artifact, unit, route, or sibling configuration. The executor must locate the exact operator-signed intent event by event id, verify NIP-01 id/signature and authorized signer at that intent’s effective time, validate its service/environment/unit/artifact/spec hash against the winning service-authored `30900`, and reject revoked, superseded, deleted, or unlinked intent/state pairs. A service-signed state record alone is not proof of operator authorization. If the current `30900` shape lacks an unambiguous intent-event link or sufficient signed spec evidence, amend the intent/state publication contract first and retain the suspension for old records. No full service specification is to be inferred from the desired hash alone.

## Input contract

Introduce a narrowly scoped canonical apply snapshot loaded by a read-only local-store adapter: service-state coordinate and winning event id; service/environment/unit identities and winning event ids; the complete `DesiredRuntimeState` with `DesiredHash`, `ArtifactID`, `DeploymentUnitID`, runtime type and stable key; all active siblings for the target deployment unit with their winning state ids; a complete unit-membership generation (or equivalent versioned membership-set digest) and its source event ids; the deterministic unit/environment plan hash; and a readiness watermark proving the relevant scoped subscriptions reached EOSE and remain healthy. Use existing event validation and replaceable winner rules in `CanonicalRuntimeSource` (`internal/reconcile/canonical_runtime_source.go`), but extend it rather than falling back to SQL when a required record is absent. Treat tombstones, missing specs, mismatched IDs, invalid hashes, conflicting unit membership, unsupported runtime, and incomplete EOSE as hard no-effect outcomes with bounded structural health metadata. The supplied spec's hash must be recomputed from its body; do not trust a self-declared hash.

Build the plan solely from complete signed sibling `DesiredRuntimeState` values. Prove membership completeness with an EOSE-fenced subscription covering every service-state coordinate that can join the environment/unit, plus a signed membership generation or a re-enumerated set digest under the effect fence; a narrow target-only subscription is insufficient. Re-enumerate the entire membership set, including newly added and tombstoned siblings, immediately before effect and after observation. Any added, removed, or changed member aborts the pre-effect plan or marks an in-flight effect superseded; never silently omit a phantom sibling. Never call the current `EnvironmentPlanAssembler.Assemble` in this path: its legacy hydration, optional persistence, and repository loaders violate authority. A shared pure grouping/revision function may be extracted. Compose applies the complete unit plan; non-Compose targets still validate unit and sibling constraints. Runtime resolution may consume canonical service/environment/unit projections, but those projections must be read-only and must not permit SQL fallback for apply. Artifact metadata is admissible only when it matches the signed spec and validated canonical artifact record; the signed spec, not a repository default artifact, decides `ImageRef` and artifact id.

`DesiredSecretRef` supplies ids and environment-variable bindings, never values. Before effect, resolve each target and sibling reference by id from a local encrypted value store/provider whose source is independent of PostgreSQL truth, check canonical `SecretRef` metadata and organization/service/environment authorization, and emit existing audited access manifests. Pin the exact secret version or ciphertext event id selected by each signed reference, validate it before and immediately after value resolution under the effect fence, and refuse a rotation or revocation race rather than mixing versions within one unit apply. A missing value, stale version, or authorization failure blocks the entire unit effect; do not reuse SQL `ListEffective`, inject redaction placeholders, cache plaintext in canonical state, or log it. The implementation must specify the exact local encrypted value backend and rotation/version pinning before re-enablement; canonical metadata alone cannot reconstruct secret bytes after a cold restart.

## Effect, commitment, and replay

Use a durable, local operation record keyed by `(environment, deployment unit, canonical plan revision, desired-state winner ids)` with states `prepared`, `effect_started`, `effect_observed`, `receipt_committed`. Persist `prepared` before any runtime mutation, with only non-secret hashes and coordinates. The external runtime apply is not transactionally atomic with relay publish; make it idempotent by stable unit target and plan revision. After effect, observe the target and commit an immutable, service-signed result/observation through the local outbox before marking the operation complete. An OK from each required relay is delivery evidence, not a reason to repeat the effect. On restart, replay a prepared/in-flight operation by observing every resource in the unit and comparing applied revision/desired hash; distinguish no effect, complete effect, and partial effect. Reapply only if observation proves the effect absent or the runtime adapter provides an idempotent, revision-fenced repair for the exact partial resource set, the canonical winner and membership are unchanged, and the apply fence can be reacquired. If observation is inconclusive or a partial effect cannot be repaired deterministically, suspend with an explicit recovery verdict, never blindly repeat. If the canonical winner changes mid-flight, record the old effect's outcome, then queue reconciliation of the new winner; never publish the old desired snapshot as current authority. SQL projection is downstream and best-effort.

The operation record is a crash-recovery journal, not a second desired-state authority. It may be rebuilt or resolved against signed state and live runtime evidence; it cannot invent desired configuration. Existing outbox idempotency/delivery contracts apply to every signed receipt. Whether the current runtime adapters expose a durable applied-revision marker sufficient for replay is an implementation gate; if not, add one before enabling auto-apply.

## Lock and TOCTOU boundary

Replace the PostgreSQL advisory `RuntimeApplyLock` for this path with a non-PostgreSQL environment/unit effect fence that serializes **both automatic and manual** deploy, rollback, restart/stop, and other runtime mutations touching the same unit. Wire manual lifecycle entry points to the same fence before enabling auto-apply; a private auto-only mutex is insufficient. Acquire the environment-scoped try-lock before loading the canonical snapshot, resolving secrets, planning, or staging any effect. Under the lock, capture winning event ids, operator-intent proof, membership generation/set digest and readiness; validate spec hashes; assemble the entire unit plan; resolve pinned secret versions; and immediately re-read the winning ids, intent revocation state, full membership set, and secret versions before `ApplyDesiredState`. Hold the lock through effect, observation, and local receipt admission. Recheck winner ids after effect and before reporting convergence. A single-process lock does not fence another daemon or an external operator; prove singleton ownership for an environment and that every manual mutation shares the same lock, or use a durable distributed lease with monotonic fencing token checked by the runtime adapter before each effect. A PostgreSQL advisory lock or SQL-dependent lease is not acceptable: absent-SQL boot must preserve the same exclusion guarantee. Without that proof, keep `auto_apply` disabled. Contention is not a deployment failure and must not escalate reconcile backoff as though an apply occurred.

## Implementation slices and ownership

1. **Canonical authorization, snapshot and pure plan** — `internal/reconcile/canonical_runtime_source.go` and tests; a new read-only snapshot/plan module in `internal/service` (or `internal/reconcile` if it avoids an import cycle). Validate operator-intent link/signature/authorization/revocation, complete signed inputs, hash, full membership closure/generation, tombstones and EOSE. No SQL fallback and no effect.
2. **Effect fence, adapter and secrets** — new canonical apply executor in `internal/service`, using existing runtime adapters but not `deployDesiredState`/`EnvironmentPlanAssembler` loaders. Supply a non-PostgreSQL fence shared by manual and automatic mutations, canonical registry projections, version-pinned independent audited secret-value resolver, pre-effect ownership checks, and unit plan. Keep user-initiated deploy behavior separate until its own SQL dependency is removed.
3. **Journal/receipt and replay** — local operation journal, signed observation/result outbox admission, applied-revision observation, crash recovery for absent/complete/partial effects and winner/membership-change handling. Define the receipt's event family/coordinate against `docs/nostr-event-implementation-guide.md` before adding any kind.
4. **Wiring** — only after slices 1–3 and fencing proofs pass: replace `WithAutoRemediationDeployer(nil)` in `internal/app/app.go` with the canonical executor, and change the health warning to reflect actual readiness. Do not modify backup acceptance or Loom stale-run code as part of this issue.

## Acceptance gates

- Unit tests reject missing/tombstoned/forged/incomplete-EOSE state; absent, forged, unauthorized, revoked, superseded or mismatched operator intent; invalid spec hash; wrong unit/artifact; phantom sibling additions/deletions; and missing/unauthorized/rotated secret versions without calling a runtime adapter.
- Integration matrix runs normal boot, crash/restart at each journal transition, and absent/divergent PostgreSQL, including concurrent manual and automatic mutation with no PostgreSQL lock. The same signed state yields the same plan hash and one converged runtime effect; SQL never changes artifact, secret binding, sibling set, route, or target.
- Deterministic concurrency tests race operator desired-state replacement or revocation, complete membership-set change (including phantom addition), secret rotation, manual deploy/rollback against auto-apply, try-lock contention, a second daemon, partial Compose/runtime effect, and receipt delivery failure. No stale plan is applied after a pre-effect winner change; replay never duplicates a confirmed effect.
- Runtime effect receipts are signed, locally admitted before relay delivery, idempotent, and contain no plaintext secret or raw provider diagnostics. `go test ./...`, `go test -race` for affected packages, and architecture ratchets pass without baseline growth. Startup with database unavailable still reaches the canonical observe-only mode; remediation only runs when scoped EOSE and fencing are proven.

## Unresolved gates

The operator-intent-to-`30900` signed linkage, complete membership generation/readiness proof, secret-value backend and rotation pin, non-PostgreSQL fence shared by manual and automatic paths, cross-daemon fencing mechanism, runtime applied-revision/partial-effect marker, and result-event contract require concrete implementation decisions. Until these are evidenced by tests, the nil deployer and operator-facing `auto_apply: suspended` health state remain the correct behavior.
