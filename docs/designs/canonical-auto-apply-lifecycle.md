# Canonical auto-apply lifecycle (`bahia-4f10q.2`)

Status: the route-free, Bahia-managed Docker auto-apply path is enabled behind `reconcile.enabled` and `direct_runtime_actions.enabled`. All other automatic effects fail closed with `bahia-4f10q.2` in the reason. This is not permission to route SQL-backed `RuntimeLifecycleService` through the reconciler.

## Authority and bounded input contract

The executor reads the daemon's local Nostr event store, not PostgreSQL. It requires a service-signed winning service state (30900) with a complete, recomputed `DesiredServiceSpec`, the matching service-signed deployment-intent registry record, service/environment and artifact registry records, and an exact operator-signed deployment decision event. A service-signed, accepted 30315 status referencing that decision event is the durable proof that the normal intent processor authorized it. For an unprotected create/rollback, the intent registry's `nostr_event_id` must identify that event. For an explicit approval, the accepted status must reference an operator `deployment/approve` event naming the same deployment intent. The state/intent/spec identities and hashes must agree. A missing, superseded, deleted, forged or unlinked input is a no-effect outcome. Once a receipt has admitted a decision, an observed stale winner produces a signed fresh-decision-required checkpoint; without an admitted receipt there is no decision snapshot to report.

The decision snapshot binds the exact decision event ID and coordinate/actor; the winning service, service-state, deployment-intent, environment and artifact event IDs; the release/artifact event ID; the desired spec and deployment-unit target; and each required secret ID, environment-variable binding, Signet credential ID and version. A route event ID/revision field exists, but the currently supported path requires no public route. Runtime-release bindings and canary release promotions have no replay-safe effect adapter yet and are refused, rather than being inferred from an artifact or SQL row. The specific signed events read are compared again under the fence before effect. Latest-wins and observed conflicts govern; no EOSE-fenced global membership or absence proof is claimed. EOSE is not absence.

Decision construction pins store-backed secret references in the signed desired spec, without fetching a value. It reads canonical secret metadata and uses Signet `Inspect` to verify the active version and tenant/service label. Those IDs and versions contribute to the desired hash. The executor requires every desired secret to have such a pin, checks the current canonical reference, then calls the Signet-backed `SecretStore.ResolveAll` at use time (`credential/deliver` with `expected_version`). A changed/revoked/missing version is `fresh_decision_required`, not a silent rotation. Values exist only in apply-scoped memory and are dropped/zeroized afterward. Old desired specs without pins remain observe-only.

The Docker adapter accepts only an auto-apply, Bahia-managed deployment unit and refuses adopted runtime configuration or plaintext secret fields. It resolves the runtime from the signed service/environment/unit values, observes the exact managed container and `bahia.desired_hash`, and passes the signed spec and resolved secrets to the desired-state applier. Compose, public-route, canary, runtime-release, tool-approval and LLM effects remain fail closed. `bahia-4f10q.2.1` owns the tool-approval extension and `bahia-4f10q.2.2` owns LLM effects; neither is implemented here.

## Non-PostgreSQL effect fence and deployment precondition

`RuntimeApplyLock` uses per-environment advisory filesystem locks beside the durable outbox. Manual deploy/rollback/restart/stop, supervised recovery, and canonical Docker auto-apply share it. The lock is taken before selecting execution inputs and held through effect, observation and local receipt admission. A failed lock never falls back to a process-local mutex. PostgreSQL advisory locks are not an effect fence.

The deployment contract is **one active daemon per service identity**. A remote signer bunker authorizes exactly one client key; local signing requires a single daemon instance. This is the same precondition adopted for backup admission in `bahia-cd0wr`; Bahia adds no epoch or lease protocol. The filesystem lock and exclusive local outbox handle are same-host defense in depth. Cross-host coordination and an external actor concurrently mutating the same target are out of scope and prohibited by deployment policy.

## Receipt, checkpoint, relay delivery and crash replay

The executor stores a secret-value-free immutable decision snapshot in a durable outbox-side control record keyed by deployment intent ID **before** any external effect. Its phases are `accepted`, `effect_started`, `effect_observed`, and `terminal`, plus fail-closed `refused`, `superseded`, and `recovery_required`. Each phase stores the exact signed kind-30315 checkpoint event in the same local record before outbox admission. If the process dies between those writes, startup re-enqueues the *same* signed event; it never signs a replacement for the same phase. NIP-01 replacement timestamps use `max(now, previous+1)` and refuse a floor more than 30 seconds ahead. The outbox owns relay OK/quorum evidence and retries delivery; a failed quorum does not authorize another runtime apply.

On restart, after canonical local catch-up, the receipt runner first restores any missing checkpoint to the outbox. It resumes nonterminal receipts under the same effect fence. If the Docker managed container already runs the pinned desired hash, an `effect_started` receipt advances to observed/terminal without another apply. A missing or ambiguous resource after `effect_started` is `recovery_required`: the executor will **not** blindly repeat a potentially partial external effect. A checkpointed or terminal decision never repeats the effect. Before reporting terminal success, the executor rereads the bound winners; a changed winner records the old effect as superseded instead of claiming current convergence. PostgreSQL is only a best-effort derived index and is never consulted for execution or replay.

The workflow coordinator's production `auto_apply` dispatch is guarded: it invokes the canonical executor with lookup identities only, and legacy direct-run recovery is prohibited for auto-apply units. If canonical input/status has not arrived yet, the attempt fails closed; the local reconciler or receipt runner retries after catch-up. Unsupported effect types cannot fall through to Loom or the SQL-backed manual lifecycle. Manual user-initiated operations retain their separate behavior while sharing the filesystem fence.

## Verification and explicit limits

Deterministic tests cover crash after effect/before checkpoint, crash after checkpoint/before outbox admission, startup terminal checkpoint repair, each bound revision moving, Signet version mismatch at use time, signed local input selection without PostgreSQL, and same-host process exclusion. Architecture ratchets prevent wiring the SQL lifecycle into auto-remediation or introducing a PostgreSQL effect lock. The full quality gates are recorded with the task handoff.

This narrow path does **not** solve Compose multi-service/partial-project replay, public route provider steps, canary rollout, runtime-release binding execution, tool approval (`bahia-4f10q.2.1`), or LLM effects (`bahia-4f10q.2.2`). Those require their own revision-fenced step adapters and tests; until then the executor names `bahia-4f10q.2` and does no effect. It also does not claim that a local event cache proves absence across relays. A deployment lacking an exact accepted status or decision-time secret pin requires a fresh signed decision.
