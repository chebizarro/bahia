# Legacy SQL-only state cutover (offline gate)

Normal Bahia startup never imports PostgreSQL rows into canonical relay/local state. Do not restore any boot-time DNS, ML, adoption, Hive-CI, security, policy, initiation, managed-instance, or F74a promotion hook to make an upgrade appear complete.

`bahia-migrate legacy-cutover` is a **read-only census**, not a data importer. It scans a repeatable-read PostgreSQL snapshot and prints JSON row counts for every known table in those eight legacy families, including `security_observable_publications` and the adoption prerequisite `org_ownership_repair`, plus pending and failed signed PostgreSQL outbox rows. Its `blockers` array names each nonempty table or outbox state with the exact count. A blocked read-only census prints the full JSON report to stdout and exits nonzero; do not interpret an exit code alone as a complete report. The `security_osv_vulnerability_cache` is deliberately excluded: it caches external OSV reference data, not Bahia intent or publication state. A missing table, SQL error, or incomplete census is an error, not an empty family. Nonzero counts are conservatively blocked because a SQL row count cannot prove that a matching relay event exists. This includes repaired ownership rows and SQL-derived mirrors; the command does not guess. The census uses a non-mutating config load; if mutable-policy environment seeds would rewrite the YAML, it fails with guidance instead.

## Procedure

1. Back up PostgreSQL and the local event store/outbox, record the Bahia image digest and relay URLs, and test restoring both backups in isolation. Do not delete SQL rows as a shortcut to a clean census.
2. Run `bahia-migrate --config config.yaml legacy-cutover > legacy-census.json` while the daemon is still available. Save the JSON report with the upgrade record even when the command exits nonzero because it found blockers. This mode writes no marker and never signs, enqueues, or publishes anything. A zero exit means only that the inventoried SQL tables and signed outbox states were empty in this snapshot, not that relay delivery is proven.
3. Stop the daemon **and every SQL writer**. Confirm that no other process can write the indexed families or PostgreSQL outbox. Run the census again. If any family is nonempty, stop: preserve the old data and keep the upgrade blocked until a separately reviewed, bounded, resumable migration with canonical conflict checks and relay acceptance proof exists for that family. The five existing `BackfillFromIndex` / `BackfillCanonicalPolicies` methods are not such a workflow; they are one-shot helpers with unbounded or incomplete delivery semantics.
4. Treat `nostr_events` pending and failed rows separately. `bahia-migrate --target default outbox-transfer` and `--target control-plane outbox-transfer` are read-only, bounded inventories. Follow `next_after` until exhausted, but note that a moving SQL source can invalidate that chain. Attempt count zero does **not** prove no relay accepted an event. There is no safe apply path until a cross-store claim protocol preserves the exact signed event and per-relay acceptance. Never discard those rows or re-sign them from SQL.
5. Only when all listed tables and both outbox counts are zero, configure the daemon's `nostr.local_store.outbox_path` (or `path` with its derived outbox) as an **absolute path**, verify that it points to the stopped daemon's existing outbox file, then run `bahia-migrate --config config.yaml --confirm-quiesced --outbox-path /absolute/daemon/outbox.bolt legacy-cutover`. The supplied path must exactly match the configured path. The command takes an exclusive lock and writes `migration/legacy-sql-empty-cutover-v1`; it will neither create a missing outbox nor rename/repair a corrupt one. If it refuses the outbox, preserve the file and investigate before retrying. An existing valid marker is checked against a fresh empty census. This marker attests only to an empty, quiesced SQL snapshot at its timestamp. It is **not** proof of migration, relay delivery, or a durable guarantee against later SQL writes.
6. Restart only after the separate F74a migration/relay-delivery gates, canonical reconciliation gates, and independent Docker/staging validation are satisfied. Keep the backups until rollback has been rehearsed. Re-run the read-only census if any SQL writer resumes before the final cutover decision.

The empty-state seal is intentionally narrow. It provides a safe cutover for a fresh or genuinely empty legacy index; populated upgrades remain blocked rather than silently losing SQL-only state. An older local marker lacking a count for `org_ownership_repair` is refused rather than silently upgraded. DNS/ML local-control bootstrap and the five orphaned one-shot migration exports must not be invoked from daemon boot or this command. A future nonempty-state migration needs bounded keyset admission, durable per-source progress, conflict detection against relay/local winners, and accepted-delivery proof before a family marker can be written.
